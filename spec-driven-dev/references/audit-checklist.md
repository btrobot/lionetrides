# Audit 检查清单

## 四维审计

audit 从四个维度检查代码与 spec 的一致性：

### 维度一：字段（Field）

| 检查项 | 检查方法 | 判定 |
|--------|---------|------|
| spec 中定义的字段在 DB schema 中存在 | 对比 `spec.yaml` fields 与 `schema.ts` 表定义 | 缺字段 → 差异 |
| 字段类型一致 | 对比类型映射（string→text, integer→integer 等） | 类型不匹配 → 差异 |
| 字段约束一致 | 对比 required/nullable/default/unique | 约束不同 → 差异 |
| 代码中使用的字段名与 schema 一致 | 搜索服务层、工厂中的字段引用 | 字段名不存在 → 差异 |

### 维度二：操作（Operation）

| 检查项 | 检查方法 | 判定 |
|--------|---------|------|
| 每个操作有对应的 API 路由 | 路由文件是否存在（`app/api/v1/.../route.ts`） | 路由缺失 → P0/P1 |
| 每个操作有对应的服务层函数 | 服务文件是否存在对应的方法 | 函数缺失 → P1 |
| HTTP 方法与 spec 一致 | 对比 route.ts 中的 export 函数 | 方法不匹配 → 差异 |
| 认证要求与 spec 一致 | 对比 route.ts 中是否使用了 withAuth/withAdmin | 权限不匹配 → P0 |
| 分页参数与 spec 一致 | 对比 list 操作是否支持 page/pageSize/total | 分页缺失 → P1 |

### 维度三：状态机（State Machine）

| 检查项 | 检查方法 | 判定 |
|--------|---------|------|
| spec 定义了状态机 | 检查 spec 是否有 state_machine 节 | 无定义 → 跳过 |
| 状态枚举在代码中实现 | 搜索代码中的状态常量/枚举 | 未实现 → P1 |
| 所有合法转换可执行 | 检查 updateStatus 等函数是否覆盖所有 transition | 转换缺失 → P0 |
| 历史记录表存在 | 检查是否有 `_history` 表 | 缺失 → P1 |
| 终端状态不可再转换 | 检查代码是否有终端状态检查 | 缺失 → P0 |

### 维度四：规则（Rules）

| 检查项 | 检查方法 | 判定 |
|--------|---------|------|
| severity=error 的规则有校验代码 | 搜索服务层中的校验逻辑 | 缺失 → P0 |
| severity=warning 的规则有校验代码 | 同上 | 缺失 → P1 |
| 校验失败时返回明确错误信息 | 检查错误消息是否包含规则 ID 或描述 | 不明确 → P2 |
| 规则有对应的测试覆盖 | 检查测试文件中是否有该规则的测试用例 | 缺失 → 补测试 |

---

## 优先级判定规则

### P0（必须立即修复 — 核心功能断裂）

- 路由不存在 → 创建路由
- 认证/授权缺失 → 添加中间件
- 主流程操作 missing（如 create/list/getById）→ 实现
- 业务规则校验缺失（severity=error 的规则）→ 添加校验
- 状态机终端状态未检查 → 添加检查

### P1（应该修复 — 功能完整性问题）

- 非核心操作 missing（如 update/remove）→ 实现
- 分页/排序/过滤缺失 → 添加
- 查询条件不完整 → 补全
- 状态机历史记录缺失 → 添加表
- 非终端状态检查缺失 → 添加

### P2（可以修复 — 工程优化）

- 类型收窄（string → 联合类型/enum）
- 枚举值硬编码 → 枚举化
- 软删除过滤不完整 → 补全
- 索引优化 → 添加复合索引
- 错误消息明确化 → 改进
- 代码中的 `as any` 绕过 → 移除
